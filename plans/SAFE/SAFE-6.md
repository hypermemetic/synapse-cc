## Problem

After plexus-transport's cookie-only WebSocket auth migration, generated TS clients that still pass tokens via URL fail silently on upgrade — the WS connection drops with no hint about why. synapse-cc has no awareness of which auth mode a backend expects, so it can't warn during build that the configured client transport is mismatched.

The result: a developer regenerates their client against a current backend, the build succeeds, the deployed client refuses every request, and the failure mode is invisible until runtime.

## Context

Once REQ-5 lands, the IR carries `psRequest` per plugin. A backend that requires cookie-based auth declares it as `auth_token: String` with `#[from_cookie("access_token")]` — visible in the IR as a `request.properties.auth_token` field with `x-plexus-source: { from: "cookie", key: "access_token" }`.

SAFE-7 makes hub-codegen's TS client cookie-capable (no URL-token construction). With both in place, synapse-cc can compare the backend's declared auth mode against the configured target's transport choice and warn on mismatch.

## Required behavior

| Inputs | Behavior |
|---|---|
| Backend's `psRequest` declares `auth_token` from cookie source AND target's generated client uses URL-token transport (legacy hub-codegen output present in target dir) | Build succeeds; emit a warning containing the substrings `cookie` and `URL` and naming the target |
| Backend's `psRequest` declares cookie auth AND target's generated client uses cookie-based transport (post-SAFE-7) | No warning |
| Backend has no `psRequest` field | No warning regardless of client transport choice |
| Backend's `psRequest` declares no auth-related field | No warning regardless of client transport choice |

Detection of the target's transport mode is observational: synapse-cc inspects the existing `transport.ts` (or equivalent) in the target's output directory, looking for the SAFE-7 marker (a comment or known function name) that distinguishes cookie-based from URL-based transports. If the file doesn't exist (first build), no warning is emitted.

## What must NOT change

- Build still succeeds on mismatch — this is a warning, not a hard failure
- No new flags introduced; the warning fires once per build, no opt-out
- Backends without `psRequest` are unaffected
- Targets configured with a custom transport (not generated by hub-codegen) are unaffected — the inspection looks for the SAFE-7 marker; absence means "not a hub-codegen client, don't warn"

## Risks

1. **Marker-based detection is fragile.** If a user hand-edits the generated transport.ts in a way that removes the SAFE-7 marker, the warning won't fire. Acceptable trade-off — the alternative (parsing TS) is heavyweight for a defensive warning. Document the marker convention in SAFE-7's output.
2. **First build has no prior client to inspect.** Skip the warning; it's not actionable until a client exists. Subsequent builds will catch the mismatch.

## Acceptance criteria

1. Build against a backend whose `psRequest` declares `auth_token` from cookie, with a target dir containing a transport.ts that lacks the SAFE-7 marker: stderr contains the substrings `cookie` and `URL` and the target name
2. Build against the same backend with a target dir containing a SAFE-7-marked transport.ts: no such warning in stderr
3. Build against a backend with no `psRequest` field: no warning in stderr regardless of target transport.ts contents
4. First build (no prior target/transport.ts present): no warning in stderr
5. Build with `--force`: warning behavior unchanged from non-force builds (this is not a cache concern)

## Completion

Implementor exercises the four observable cases via live backends or fixtures and includes one stderr capture for the warning case in the commit. Flips status to Complete.

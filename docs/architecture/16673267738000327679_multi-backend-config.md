# Multi-Backend + Plugin Filtering in synapse.config.json

## Problem

Two related limitations in `synapse.config.json`:

1. **Single backend per config** — `backend` and `url` are top-level, shared by all targets. Projects that need clients from multiple backends (e.g., monochrome + substrate) must swap config files.

2. **No plugin filtering** — generating from substrate produces all 35 plugins when you only need `claudecode`. The extra 34 plugin dirs are dead weight.

### Motivating Example

mono-tray connects to monochrome (`:4448`, music player) and substrate (`:4444`, claudecode for AI research). Today requires two config files and a swap hack:

```bash
cp synapse.config.json synapse.config.json.bak
cp synapse.substrate.config.json synapse.config.json
synapse-cc build
cp synapse.config.json.bak synapse.config.json
rm synapse.config.json.bak
```

This is fragile, race-prone, and generates 89 files when 6 are needed.

## Current Schema (v1.0)

```json
{
  "schema": "1.0",
  "language": "typescript",
  "backend": "monochrome",
  "url": "ws://127.0.0.1:4448",
  "targets": {
    "client": {
      "generate": ["transport", "rpc", "plugins"],
      "transport": "browser",
      "outputDir": "generated"
    }
  }
}
```

`backend`/`url` are `Maybe Text` on `SynapseConfig`. `TargetConfig` has no backend, url, or plugin filter fields. `buildConfigFromTarget` reads the single top-level backend for every target.

## Proposed Schema (v1.1)

Two new per-target fields: `backend`/`url` override + `plugins` filter list.

```json
{
  "schema": "1.1",
  "language": "typescript",
  "backend": "monochrome",
  "url": "ws://127.0.0.1:4448",
  "packageManager": "bun",
  "targets": {
    "client": {
      "generate": ["transport", "rpc", "plugins"],
      "transport": "browser",
      "outputDir": "generated"
    },
    "substrate-claudecode": {
      "backend": "substrate",
      "url": "ws://127.0.0.1:4444",
      "plugins": ["claudecode"],
      "generate": ["transport", "rpc", "plugins"],
      "transport": "browser",
      "outputDir": "generated-substrate"
    }
  }
}
```

This single config replaces two config files. `synapse-cc build` connects to both backends and generates exactly what's needed.

### What `plugins` does

The `plugins` field is an allowlist of plugin namespaces to generate. Omitting it (or `"plugins": null`) generates all plugins (current behavior).

```json
"plugins": ["claudecode"]           // only claudecode
"plugins": ["claudecode", "cone"]   // claudecode + cone
"plugins": null                     // all (default)
```

## The Type Dependency Problem

Plugin filtering isn't just "skip these dirs." The IR has cross-plugin type references:

```
claudecode/types.ts → imports { Position, UUID } from ../cone/types
```

`UUID` and `Position` are deduplicated into the `cone` namespace by the IR builder (shortest namespace wins). So `claudecode` has a hard dependency on `cone`'s type definitions, even though it never calls cone methods.

### Solution: Automatic Type Dependency Resolution

When `plugins: ["claudecode"]` is specified:

1. **Generate full client** for `claudecode` (client.ts, types.ts, index.ts)
2. **Walk type references** in claudecode's types — find all cross-namespace `RefNamed` references (e.g., `cone.UUID`, `cone.Position`)
3. **Generate types-only stubs** for referenced namespaces — emit `cone/types.ts` with just the referenced type definitions, but **no `cone/client.ts`** (no RPC methods)
4. **No index.ts re-export** for stub namespaces — they're internal dependencies, not public API

Result for `plugins: ["claudecode"]`:

```
generated-substrate/
  transport.ts          # shared transport
  rpc.ts                # shared RPC layer
  types.ts              # shared Plexus types
  index.ts              # re-exports claudecode only
  claudecode/
    client.ts           # full typed client
    types.ts            # all claudecode types
    index.ts            # re-exports
  cone/
    types.ts            # types-only stub (UUID, Position only)
```

Later, adding `"plugins": ["claudecode", "cone"]` promotes `cone/` to a full plugin with `client.ts` + `index.ts`.

### How it slots together

The namespace structure is stable. Adding plugins to the filter never moves files or changes import paths:

- `claudecode/types.ts` always imports from `../cone/types` regardless of whether cone is a stub or full plugin
- Adding `"cone"` to the plugins list adds `cone/client.ts` and `cone/index.ts` — it doesn't touch `cone/types.ts` (already exists as stub)
- Removing `"cone"` from the filter deletes `cone/client.ts` and `cone/index.ts` but keeps `cone/types.ts` (still needed as dependency)
- The top-level `index.ts` only re-exports plugins in the filter list, not stubs

## Changes Required

### 1. `Types.hs` — Add fields to `TargetConfig`

```haskell
data TargetConfig = TargetConfig
  { tcGenerate   :: ![Text]
  , tcTransport  :: !TransportType
  , tcOutputDir  :: !FilePath
  , tcSmokePath  :: !(Maybe Text)
  , tcBackend    :: !(Maybe Text)        -- NEW: per-target backend override
  , tcUrl        :: !(Maybe Text)        -- NEW: per-target URL override
  , tcPlugins    :: !(Maybe [Text])      -- NEW: plugin allowlist (Nothing = all)
  }
```

All three are `Maybe`, parsed with `.:?`. Omitting them = inherit top-level / generate all.

### 2. `Config.hs` — Update `buildConfigFromTarget`

Prefer per-target backend/url, fall back to top-level:

```haskell
buildConfigFromTarget opts sc tc =
  let url         = fromMaybe (fromMaybe "ws://127.0.0.1:4444" (scUrl sc)) (tcUrl tc)
      (host, port) = parseWsUrl url
      backendName = fromMaybe (fromMaybe "" (scBackend sc)) (tcBackend tc)
  in Config { ... }
```

### 3. `Config.hs` — Update `validateSynapseConfig`

Relax validation: a target is valid if it has a backend+url from **either** its own fields or the top-level.

| Top-level backend | Target backend | Target generate  | Valid? |
|-------------------|----------------|------------------|--------|
| present           | absent         | ["plugins", ...] | yes    |
| absent            | present        | ["plugins", ...] | yes    |
| present           | present        | ["plugins", ...] | yes (target wins) |
| absent            | absent         | ["plugins", ...] | **no** |
| absent            | absent         | ["transport"]    | yes    |

### 4. Plugin filtering — where it happens

This is the key question: does filtering happen in synapse (IR generation), hub-codegen (code generation), or synapse-cc (orchestration)?

**Recommended: filter in hub-codegen.** The IR should contain all plugins (complete schema). hub-codegen receives the full IR + a plugin allowlist and:

1. Generates client + types for allowed plugins
2. Walks type refs to find dependency namespaces
3. Generates types-only stubs for dependencies not in the allowlist
4. Generates `index.ts` re-exporting only allowed plugins

This keeps the IR truthful (full schema) and makes filtering a presentation concern.

**Passing the filter:** synapse-cc already invokes hub-codegen as a subprocess. Add a `--plugins` flag:

```bash
hub-codegen --target typescript --transport browser --plugins claudecode < ir.json
```

Multiple plugins: `--plugins claudecode,cone` (comma-separated) or repeated `--plugins claudecode --plugins cone`.

### 5. `hub-codegen` changes (`src/generator/typescript/`)

#### a. CLI: add `--plugins` flag

```rust
#[arg(long, value_delimiter = ',')]
plugins: Option<Vec<String>>,
```

#### b. `mod.rs` / entry point: filter plugin list

After loading IR, partition namespaces into "requested" vs "type-dependency-only":

```rust
let requested_plugins: HashSet<&str> = match &args.plugins {
    Some(list) => list.iter().map(|s| s.as_str()).collect(),
    None => ir.methods.keys().map(|k| k.namespace()).collect(), // all
};

// Walk type refs from requested plugins to find dependencies
let type_deps = resolve_type_dependencies(&ir, &requested_plugins);
// type_deps = set of namespaces needed for types but not in requested_plugins
```

#### c. `types.rs`: generate types for requested + dependency namespaces

No change to type generation itself — just which namespaces get types generated.

#### d. `client.rs`: generate clients only for requested plugins

Skip `client.ts` generation for namespaces in `type_deps` but not in `requested_plugins`.

#### e. `index.rs`: re-export only requested plugins

Top-level `index.ts` only lists plugins from `requested_plugins`, not type-dep stubs.

### 6. `Pipeline.hs` — Pass plugins filter to hub-codegen

`synapse-cc` reads `tcPlugins` from the target config and passes it as a CLI flag when invoking hub-codegen. The IR generation (synapse) is unchanged — full schema always.

### 7. Watch mode (`Watch.hs`)

Watch currently takes a single backend. With per-target backends, watch would need to poll multiple backends. **Stretch goal** — for now, watch can use the `--target` flag to pin to a single target.

## Type Dependency Resolution Algorithm

```
resolve_type_dependencies(ir, requested_plugins):
  needed_namespaces = {}

  for each type in ir.types:
    if type.namespace in requested_plugins:
      for each ref in type.all_refs():
        if ref is RefNamed and ref.namespace not in requested_plugins:
          needed_namespaces.add(ref.namespace)

  # Transitive: dependency types may reference other namespaces
  repeat until stable:
    for each ns in needed_namespaces:
      for each type in ir.types where type.namespace == ns:
        for each ref in type.all_refs():
          if ref.namespace not in requested_plugins and ref.namespace not in needed_namespaces:
            needed_namespaces.add(ref.namespace)

  return needed_namespaces
```

In the claudecode case: claudecode refs `cone.Position` and `cone.UUID`. Position refs `cone.UUID`. Both are in `cone`, so the dependency set is `{cone}`. Stable after one iteration.

## Backward Compatibility

- v1.0 configs work unchanged (`tcBackend`, `tcUrl`, `tcPlugins` all default to `Nothing`)
- `hub-codegen` without `--plugins` generates everything (current behavior)
- No CLI changes to synapse-cc
- `synapse-cc init` continues scaffolding v1.0-style configs
